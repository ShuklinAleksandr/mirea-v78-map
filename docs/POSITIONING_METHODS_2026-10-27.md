# Как объединить источники положения на В78

27 октября 2026 года. Это проверка доступных методов и проект следующего пилота. Документ не подтверждает точность в вузе, автоматический этаж или готовность нового алгоритма. Реальные радиозамеры В78 ещё не получены. Сборщик описан в [WIFI_SURVEY.md](WIFI_SURVEY.md), исходные сведения о сети — в [INDOOR_POSITIONING_2026-10-26.md](INDOOR_POSITIONING_2026-10-26.md).

## Практическое решение

**Объединить источники можно. Для В78 разумен гибрид: системная геопозиция снаружи, известная ручная точка и этаж при входе, затем радиопривязки и датчики движения внутри.** Это предлагаемая архитектура, которую нужно проверять на настоящих телефонах и независимых проходах. Одной кнопки подключения к общей сети для этого недостаточно.

Нужно раздельно хранить положение `[x,z]`, корпус, физический этаж, время, источник и неопределённость. Открытый на экране этаж не служит измерением этажа пользователя. При отсутствии уверенного результата показывается последнее положение с явным статусом или просьба уточнить место.

| Источник                         | Что даёт                                                                      | Что необходимо для В78                                                          |
| -------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Системная геопозиция             | Начальная привязка к территории; ОС уже может объединять несколько источников | Проверить реальную погрешность и геопривязку плана                              |
| Ручное «Я здесь» и «Мой этаж»    | Известное начало внутри здания                                                | Пользователь подтверждает фактическую точку и этаж                              |
| Радиокарта BSSID/RSSI на Android | Повторная привязка к обследованной зоне, возможная оценка этажа               | Замеры в известных местах на разных этажах и независимая проверка               |
| Шаги и направление               | Оценка перемещения между достоверными привязками                              | Нативные датчики, проверка положения телефона и накопления ошибки               |
| Барометр                         | Изменение высоты относительно начала измерения                                | Датчик, подтверждённый начальный этаж, обследованные перепады высоты            |
| Проверенная карта проходов       | Ограничение допустимых гипотез                                                | Подтверждённые стены, двери и лестничные связи; разрывы графа не дорисовываются |

Android Fused Location Provider и Apple Core Location уже используют системные источники, поэтому название кнопки «GPS» упрощает фактический способ получения точки. Эти API не предоставляют готовую радиокарту В78. См. [Google Fused Location Provider](https://developers.google.com/location-context/fused-location-provider) и [Apple TN3111](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview).

## Почему этаж требует отдельной логики

На iPhone `CLLocation` иногда содержит `CLFloor`, если система может определить уровень. Доступность на В78 не подтверждена. `CLFloor.level` использует логические уровни относительно земли, начиная с `0`; они не обязаны совпадать с номерами на указателях здания. Их нельзя напрямую подписывать как местные «1/2/3 этаж». См. [CLFloor](https://developer.apple.com/documentation/corelocation/clfloor) и [CLFloor.level](https://developer.apple.com/documentation/corelocation/clfloor/level).

Барометр пригоден для оценки **изменения** высоты. Apple предоставляет `relativeAltitude` относительно первого измерения, Android — расчёт разности высот по давлению. Абсолютный номер этажа из этого не следует. Предлагаемое поведение: пользователь подтверждает начальный этаж; при согласованном изменении высоты приложение предлагает проверить переход. Автоматическое переключение вводится только после полевого теста. Измеренные высоты этажей В78 сейчас отсутствуют. См. [Apple CMAltimeter](https://developer.apple.com/documentation/coremotion/cmaltimeter), [relativeAltitude](https://developer.apple.com/documentation/coremotion/cmaltitudedata/relativealtitude) и [Android SensorManager.getAltitude](<https://developer.android.com/reference/android/hardware/SensorManager#getAltitude(float,float)>).

## Wi-Fi и движение: ограничения платформ

На Android радиокарту можно строить по повторным наблюдениям BSSID/RSSI в известных точках, включая коридоры. Для такого проекта координаты самих роутеров не обязательны. Но активные сканы Android 9+ ограничены четырьмя запросами за две минуты у видимого приложения; данные могут быть старыми. Android 10+ также позволяет слушать завершение системных сканов, но не обещает нужную частоту. Поэтому одни сканы не обеспечивают плавную движущуюся точку. См. [Android Wi-Fi scanning](https://developer.android.com/develop/connectivity/wifi/wifi-scan).

Для промежутков можно исследовать pedestrian dead reckoning: события шага и изменение направления от датчиков. Наличие датчиков зависит от телефона. Android требует разрешение `ACTIVITY_RECOGNITION` для счётчика/детектора шагов; Core Motion требует соответствующее описание доступа и проверку наличия оборудования. Предлагаемая оценка движения должна терять уверенность без новых привязок. Её нельзя объявлять точным местоположением только потому, что точка движется. См. [Android motion sensors](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion) и [Apple Core Motion](https://developer.apple.com/documentation/coremotion/).

На iOS нет общего публичного API сканирования соседних Wi-Fi-сетей. Hotspot Helper не является обходом для Wi-Fi-позиционирования; Wi-Fi Aware решает задачи связи с устройствами. Поэтому Android-сборщик нельзя просто перенести на iPhone. См. [Apple TN3111](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview).

Реальный системный путь Apple для обследованного здания — Indoor Maps Program: карта IMDF, Indoor Survey, обработка и активация, затем проверка. Он требует участия владельца или оператора здания. Apple описывает сочетание Wi-Fi-отпечатков с локальными датчиками; это подтверждает пригодность гибридного подхода, но не его наличие у нашего приложения. См. [Apple: Introducing the Indoor Maps Program](https://developer.apple.com/videos/play/wwdc2019/245/).

## Более сложные методы

- **Wi-Fi RTT / 802.11mc и 802.11az:** измерение расстояний вместо оценки по мощности сигнала. Нужны совместимые телефон и точки доступа; координаты AP — заранее известные либо предоставленные оборудованием через LCI/LCR. Поддержка сети вуза не проверена. См. [Android Wi-Fi RTT](https://developer.android.com/develop/connectivity/wifi/wifi-rtt).
- **UWB:** точное относительное измерение до совместимых устройств; для покрытия здания нужна установленная инфраструктура с известной привязкой. Обычные Wi-Fi-роутеры её не заменяют. На iPhone есть Nearby Interaction и отдельный путь DL-TDOA с физическими якорями; доступность API/функции проверяется для фактических ОС, SDK и телефона. См. [Apple Nearby Interaction](https://developer.apple.com/documentation/nearbyinteraction/) и [DL-TDOA ranging](https://developer.apple.com/documentation/nearbyinteraction/dl-tdoa-ranging).
- **Визуальные якоря камерой:** позволяют повторно найти заранее обследованное место и продолжить относительное движение. Например, Cloud Anchors требуют визуальной съёмки, совместимого устройства, камеры и интернета; это отдельный режим взаимодействия. Глобальный VPS по Street View не доказывает покрытие коридоров В78. См. [ARCore Cloud Anchors](https://developers.google.com/ar/develop/cloud-anchors) и [ARCore Geospatial](https://developers.google.com/ar/develop/geospatial).

## Следующий проверяемый шаг

1. Завершить честное отображение системных обновлений, ручного этажа и точки уточнения во всех режимах карты. Временная ручная поправка GPS остаётся приблизительной: она не превращает нестабильные GPS-приращения в измеренное движение по коридору.
2. Обследовать один корпус и два соседних физических этажа Android-телефонами: коридоры, повороты, подходы к лестницам. Сохранить известные места, повторные серии, возраст сканов и модель телефона. Больше одинаковых записей в одной точке не гарантирует улучшение; нужны покрытие и разнообразные независимые условия.
3. На отдельном наборе проверить распознавание зон/этажей и долю отказов. После пригодной радиокарты отдельно записать шаги, направление и давление на контрольных проходах и сравнить гибрид с одним источником. Оценивать ошибки, неверные этажи, задержку, отказы и батарею. Алгоритм объединения выбирается по данным; сам по себе фильтр Калмана или фильтр частиц не создаёт отсутствующую информацию.
4. Для iPhone отдельно выяснить готовность вуза участвовать в Apple Indoor Maps Program либо рассматривать инфраструктурный пилот. До этого сохранять ручное подтверждение этажа и честный статус системной точки.

Установка новых маяков, QR, получение секретов сети и обещания точности в этот шаг не входят.
